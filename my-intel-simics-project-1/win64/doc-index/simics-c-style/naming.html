6 Naming

In absence of other rules, identifiers are written in lower case letters, words separated by underscores.

6.1 Functions, macros and variables

Functions and macros that are executed primarily for their side-effect should be named after what they do. Functions and macros executed for their return value should be named after what they return. If the function or macro is a predicate (returning a boolean value), it should be named after the condition when it returns a true value.

Examples:

void show_death_animation(monster_t *m);
float magic_power(monster_t *m, int colour);
bool is_undead(monster_t *m);

Variables should be named after what they contain, not from the variable or its type. The more local a variable is, the shorter can be its name. Use long, descriptive names for global variables; use short names in local scopes. Names more frequently used can also be shorter.

Do not append a number as a general method to create new identifiers, other than in very special circumstances:

void draw_line(int x1, int y1, int x2, int y2); /* good */
int invalidate_object2(conf_object_t *obj);     /* BAD */

In particular, do not use “tmp” or “ptr” in identifiers; it is rare that it is needed to point out that a variable contains a temporary value or a pointer.

Do not prefix names with an article, such as an_object or the_score.

6.2 Types

Enum members are capitalised, each word separately. To avoid namespace clashes, consider using a common prefix:

enum monster_state { Sleeping, Awake, Angry, Fleeing };
enum shape { Sh_Rect, Sh_Rounded_Rect, Sh_Circle };

Typedef names should end in _t. Typedef structs, unions and enums unless only used locally. Do not define tags unless needed. If a struct/enum/union tag is defined, make it equal to the typedef but without the _t suffix.

Where possible, make struct definitions private to code if other parts of the source only need to handle pointers to the struct.

6.3 Files

In file names, words are separated by hyphens rather than underscores.
