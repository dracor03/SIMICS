8 Various issues

Avoid assignments inside expressions, unless needed for flow control reasons:

if ((err = hurt_enemy(e)) < 0) ...           /* BAD */

err = hurt_enemy(e);
if (err < 0) ...                             /* GOOD */

while ((victim = next_target()) != NULL) ... /* GOOD */

This makes the expressions simpler to analyze and immediately understand; side-effects require some further thought. It also saves on parentheses and line length.

Use NULL instead of 0 as a null data pointer. Use (type *)0 as a null function pointer.

NULL is a pointer, 0 is an integer; the choice sends a strong message to the reader about the intention of the code. Unfortunately, the use of NULL as a function pointer cannot be used in portable C, hence the need to use 0, cast as appropriate. Using 0 instead of a pointer type as argument to a vararg function is undefined and can (and will) cause crashes.

Avoid casts where possible, since this can hide errors while suppressing warnings:

  • Do not cast pointers to/from void *
  • Use intermediate variables to convert a void * to a specific pointer.
  • Take the address of substructures instead of casting struct pointers.

Examples:

void *p = ...
int strength = ((troll_t *)p)->strength;   /* BAD */

troll_t *t = p;
int strength = t->strength;                /* GOOD */

save_object((conf_object_t *)cpu);         /* BAD */
save_object(&cpu->obj);                    /* GOOD */

When comparing an expression against a constant, put the constant last:

if (2 == x) ...              /* BAD */
if (x == 2) ...              /* GOOD */

This is more intuitive and scans better, since it corresponds more closely to how you would pronounce it in natural language (“if x is equal to two”, never “if two is equal to x”, since “two” is not likely to change.)

8.1 Switch statements

Always indicate a switch case fall-through with a comment.

switch (monster->state) {
case Sleeping:
        wake_up(monster);
        /* FALLTHROUGH */
case Awake:
        attack(monster, player);
        break;
case Dead:
        rattle_bones(monster->corpse);
        break;
}

All other cases should have a break statement, even the last case in the switch, unless they use a return/continue/goto to transfer control elsewhere.

Blocks inside switch clauses, when needed for local variables, do not introduce a new indentation level:

switch (cmd.type) {
case Sail: {
        double distance = hypot(cmd.x, cmd.y);
        double direction = atan2(cmd.y, cmd.x);
        go(direction, distance);
        break;
}
case Anchor:
        drop_anchor(current_position);
        break;
}

8.2 Boolean expressions

You may use implicit comparison against 0 in conditions for boolean values only. This includes pointers and other values where 0 can be interpreted as falsehood:

typedef enum { Red, Blue } colour_t;
colour_t halo_team(player_t *p);
...
if (halo_team(p)) ...          /* BAD - not a boolean */

monster_t *m = make_gelatinous_cube();
if (m) ...                     /* Good - NULL is false */

For example, a function returning zero on failure and a positive result otherwise could be used in boolean context.

Expressions where 0 is not intuitively understood as false must always use explicit comparisons. In particular, the strcmp function does not return a boolean value:

if (!strcmp(login, "root")) ...      /* BAD */
if (strcmp(login, "root") == 0) ...  /* GOOD */

This is also true for calls that return -1 on failure and 0 on success:

if (rmdir(game_dir)) ...                 /* BAD */
if (rmdir(game_dir) == -1) ...           /* GOOD */
if (rmdir(game_dir) < 0) ...             /* GOOD */
