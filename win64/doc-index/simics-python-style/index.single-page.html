Style Guide for Python

This document contains style guidelines for writing Python code.

1 Introduction

These style rules are based on PEP 8 (http://www.python.org/peps/pep-0008.html), with some changes and additions. That document is well worth reading in its own right.

2 Code organisation

Avoid statements with side-effects (that is, ones that do not just declare functions or classes) at the top-level of a file. Instead, put all actual actions inside functions, and call them from a single place, usually near the bottom of the file.

For free-standing programs, write something like:

def main():
    ... code for the actual action here ...

if __name__ == "__main__":
    main()

This way, the file can be imported as a module from other files without running anything. It can also be checked by pychecker, which is highly recommended.

Use a separate line for each imported module:

import sys, os           # WRONG

import sys               # RIGHT
import os

This makes code diffs cleaner and reduces the risk for conflicts when merging changes.

Use import instead of execfile to get code and definitions from other files.

3 Layout and lexical details

The indentation step is 4 spaces. Do not use tabs. Keep lines shorter than 80 characters.

Put a space:

  • around binary operators such as +
  • after but not before comma, colon or semicolon
  • after the assert statement
  • between a keyword (such as while) and its argument

Put no space:

  • before comma, colon or semicolon
  • immediately inside parentheses, braces or brackets
  • between the function name and the opening parenthesis in a function call

It is customary to not put spaces around = inside parameter lists of function calls and definitions, but it is permitted to use a single space on each side if that makes the code look nicer:

draw(figure, options =None, paper= "A4")          # BAD
draw(figure, options=None, paper="A4")            # GOOD
play(frequency = f0 + delta, duration = d + 0.5)  # GOOD

Put spaces around colons when used in sliced indexing, but not where an index is omitted:

a[i + 1:j + 5]        # BAD
a[i + 1 : j + 5]      # GOOD

a[ : j + 5]   	      # BAD
a[:j + 5]     	      # BAD
a[: j + 5]    	      # GOOD

a[i + 1:]             # BAD
a[i + 1 : ]           # BAD
a[i + 1 :]            # GOOD

a[i + 1:j + 5:s]      # BAD
a[i + 1 : j + 5 : s]  # GOOD

a[i + 1::s]           # BAD
a[i + 1 : : s]        # BAD
a[i + 1 :: s]         # GOOD

If neither index contains spaces, the spaces around colon may be omitted, per PEP8:

a[i : j]         # OK
a[i:j]           # OK
a[i + c:j + d]   # BAD

To fold long lines, it is usually better to use parentheses rather than backslashes. I.e., instead of:

result = extremely_long_expression \
         + another_very_long_expression \
         + yet_another_long_expression

please use:

result = (extremely_long_expression
          + another_very_long_expression
          + yet_another_long_expression)

Long lines are broken before binary operators, not after.

Avoid C-isms such as parentheses around the condition of if statements or terminating semicolons.

In multi-line lists, put a trailing comma after each element, even the last one:

muppets = [
    "Kermit",
    "Miss Piggy",
    "Gonzo",
]

This way, there is less of a risk of forgetting a comma when adding an element at the end, and diffs and merges become neater.

4 Structures of data

To group a few values together, use a tuple:

t = (a, b, c)

But do not access a value from such a tuple by index, as in:

b = t[1]   # BAD

Rather, use destructuring assignment to unpack tuples:

(a, b, c) = t

This works in for loops, comprehensions and function parameters as well. Note that tuples are immutable; for mutable groups of values, define a class.

Note that while the Python language accepts omission of the parentheses around tuples, they should always be present as a matter of style:

a, b = c, d            # BAD
(a, b) = (c, d)        # GOOD

As an alternative, use a class:

class Node: pass
...
t = Node()
t.a = 17
t.b = 69

This works better when the number of values is large since the members are named. It also allows mutation.

If the class is constructed frequently, add an init method:

class Node:
    def __init__(self, a, b):
        self.a = a
        self.b = b
...
t = Node(17, 69)

5 Variables

Avoid global variables. In particular, do not use them as a way to pass parameters. Using variables that are initialised once and never changed can be acceptable:

address_cache = {}         # Only initialised, then never assigned to
def lookup_address(desc):
    if desc not in address_cache:
        address_cache[desc] = calculate_address(desc)
    return address_cache[desc]

but most uses of the global keyword are a sign that something is wrong. Consider using a class or object instead; this way, all state is contained in one place and it is clear which functions have access to it. This also makes the code easier to test.

As Python supports multiple return values (using tuples), most code can be written in a fairly functional style, passing all needed information explicitly between functions.

6 Loops

Prefer list/generator comprehensions to explicit loops. So, instead of:

s = ""
for x in mylist:
    s = s + x.description    # CLUMSY

better write:

s = "".join(x.description for x in mylist)   # NEATER

This may also be more efficient, since strings are immutable in Python and each concatenation must allocate a new one.

Also prefer comprehensions to map and filter with lambda expressions:

pyfiles = filter(lambda f: f.endswith(".py"),
                 map(lambda f: os.path.join(mydir, f),
                     files))                            # CLUMSY
pyfiles = [os.path.join(mydir, f) 
           for f in files if f.endswith(".py")]         # BETTER

Use the fact that many objects, such as files, are directly iterable:

for line in file(filename):
    dostuff(line)

The file will be closed automatically when the for statement terminates.

7 Exceptions and finishing

Be precise in what exceptions are caught to avoid hiding bugs. It is very rarely a good idea to catch all exceptions:

try:
    x = something()
except:                  # BAD
    x = theother

Put as little code as possible inside try clauses, to avoid catching exceptions you did not anticipate.

Do not use the old string-based exceptions; always raise class-based exceptions.

Avoid using exceptions to handle missing elements in dictionaries; there are usually a method that gives a cleaner solution:

try:                               # BAD
    x = pet[name]
except KeyError:
    x = little_piggy

x = pet.get(name, little_piggy)    # GOOD

In general, exceptions are preferred for errors and non-local conditions and control transfer rather than for local control flow, since they are harder to follow than plain conditionals.

To run clean-up code (such as closing files, deleting temporary things, etc), either use the try..finally construct or the with construct, instead of trying to cover all possible exit paths from a chunk of code.

8 Comments

The general rules are the same for Python as in general programming:

  • Comments should only contain information that cannot be easily inferred from the code. Clear code needs no comments.
  • Explain why, not what. In other words, describe why the code was done the way it was rather than what it does.
  • Comment data, not code. If variables and data structures are known, then the code manipulating them is easy to understand. The converse is not true.
  • Describe invariants, both in code and in data structures. If invariants can be tested in code (using assert statements, for instance), then that is even better than describing it in comments. Because assert is a statement it should be followed by a space.
  • Comment interfaces (in a general sense, not the Simics sense). For instance, a function should have a comment describing what it does and what it returns, unless obvious from the context.
  • Do not keep history in comments. The code should be described as it is, not as it has been. Erase anything that is not directly related to the current state of the code.
  • Do not keep dates or names of people in the code. It should not matter when or by whom code was written.
  • Refer to documents (such as reference manuals) as precisely as possible. It must be possible to locate the referred text from the comment alone.

Code should not be disabled by commenting it out - code that for some reason is disabled should either be removed entirely, or be left in with a suitable condition that explains why:

if debugging:
    print("raising IRQ 15")

8.1 API documentation

Exported functions and types should be documented in a way that the Simics documentation tool can parse:

def str_number(text):
    """convert a string to a number.

    Converts a string returned from [`cli.number_str`] back to an integer.

    ## Return Value
    A number representing the string.

    ## EXCEPTIONS
    **ValueError** is raised for invalid arguments.
    """

9 Naming

In general, identifiers are written in lower-case letters, words separated by underscores. Class names should start with an upper-case letter.

Constants or variables that represent quantities that are conventionally written in upper case may be written that way in Python as well.

  • Variables are named after what they contain, not by their type. Local variables can be arbitrarily short, as long as it is clear what their purpose is.
  • Functions that are mainly executed for their side-effects should be named after what they do.
  • Functions executed for their return value should be named after what they return. Predicates (functions returning a boolean value) should be named after the condition when true.

Examples:

physical_address_bits = 48         # a variable
raise_interrupt(level)             # a function with side-effects
csum = checksum(packet)            # a function without side-effects
if not valid_request(req):         # a predicate
    set_error_flag()

10 Other considerations

Use string methods wisely. There is often a function that does what you need, so look in the manual before writing a loop.

In particular, do not use indexing and slicing when testing for prefixes/suffixes. Use startswith()/endswith() instead:

if s[:3] == 'bar':       # BAD
if s.startswith('bar'):  # GOOD

Regular expressions are powerful but tricky to get right and can be slow; only use them when no better alternative exists. In particular, the string .split() method is a fast and easy way to break up a string into parts.

Always use raw string literals when specifying regular expressions:

m = re.match("[a-z]+\b", s)        # BAD (and incorrect!)
m = re.match(r"[a-z]+\b", s)       # GOOD (and correct)

If you must compare object types, use isinstance() rather than using type() since it allows for subtyping:

if type(x) == type(1):   # BAD
if isinstance(x, int):   # OK

Remember that the empty list, tuple and dict are false in boolean contexts. Use this for clearer code:

if len(mylist) > 0:      # CLUMSY
if mylist:               # BETTER

Of course, you must be sure that you test the right thing; a polymorphic variable could hold a string or None, for instance.

Keep in mind that tuples with a single element require a trailing comma:

print("Value=%r" % (value))      # WRONG
print("Value=%r" % (value,))     # RIGHT

(Consider what happens in the code above if value is a tuple.)

Use the // operator, not /, for integer (truncating) division. This makes the code more robust and also makes a migration to Python 3.x easier.

11 Using Python with Simics

Use magic attributes to access objects, attributes and interfaces by name, rather than SIM_ functions:

x = conf.cpu0.attr.pc                                # GOOD
x = SIM_get_attribute(SIM_get_object("cpu0"), "pc")  # BAD

obj.iface.foo_interface.frobble()                    # GOOD
SIM_get_interface(obj, "foo_interface").frobble()    # BAD

name = obj.name                                      # GOOD
name = SIM_object_name(obj)                          # BAD

classname = obj.classname                              # GOOD
classname = SIM_get_class_name(SIM_object_class(obj))  # BAD

But using the SIM_ functions is better than constructing a string and eval():

x = eval("conf.%s.%s[0x%xL]" % (name, attr, addr))       # BAD
x = SIM_get_attribute(SIM_get_object(name), attr)[addr]  # GOOD

In general, avoid eval() where possible as a matter of style. It includes too many opportunities of breaking abstraction barriers.
