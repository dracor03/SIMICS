Style Guide for C++

1 Introduction

This document outlines the C++ coding style guidelines for writing C++ code. Our style guide is based on the Google C++ Style Guide up to Commit 8c4da23 on Sep 5 2024 with some modifications to better suit Simics modeling.

2 Modifications

The following sections document the differences between our style guide and the Google C++ Style Guide. These modifications reflect Simics modeling’s specific requirements and preferences.

2.1 C++ Version

In addition to the guidelines provided in the Google C++ Style Guide, we want to emphasize that the choice of the C++ version should follow the specific requirements of the product. For example, the C++ API requirements lists the supported C++ standards of the Simics C++ API.

2.2 Header Files

2.2.1 The #define Guard

  • Google Style:
    • Do not use #pragma once; instead use the standard Google include guards.
    • To guarantee uniqueness, they should be based on the full path in a project’s source tree. For example, the file foo/src/bar/baz.h in project foo should have the following guard:
#ifndef FOO_BAR_BAZ_H_
#define FOO_BAR_BAZ_H_

...

#endif  // FOO_BAR_BAZ_H_
  • Simics Style:
    • Since Simics Model Builder depends on a modern C++ compiler, #pragma once is not a problem. This is the preferred choice due to its simplicity. Old style header guards are also allowed.
    • At least one directory should be part of the guard name; in the above example, BAR_BAZ_H would be permitted but not just BAZ_H. The comment after the #endif is optional but must, if present, match the guard name used.

2.2.2 Names and Order of Includes

  • Google Style: All of a project’s header files should be listed as descendants of the project’s source directory without use of UNIX directory aliases . (the current directory) or .. (the parent directory).

  • Simics Style: For headers in the same directory as the including file, it is fine to use unqualified names (#include "abc.h").

2.3 Scoping

2.3.1 Namespaces

  • Google Style: Namespaces should have unique names based on the project name, and possibly its path.

  • Simics Style: Use the simics namespace exclusively when developing or modifying a Simics product. Don’t use it in other contexts.

2.4 Google-Specific Magic

2.4.1 cpplint

  • Google Style: Use cpplint.py to detect style errors.

  • Simics Style: Because Simics includes modifications to the Google style guide, the following filters must be applied to run cpplint.py:

    • -build/header_guard, see The define Guard;
    • -build/include_subdir, see Names and Order of Includes;
    • -whitespace/indent, see Spaces vs. Tabs.

2.5 Other C++ Features

2.5.1 Exceptions

  • Google Style: Do not use C++ exceptions. Because most existing C++ code at Google is not prepared to deal with exceptions.

  • Simics Style: Appropriate use of C++ exceptions is fine in Simics. For example, in the C++ API v2, exceptions are used to indicate an error when setting an attribute.

void SampleAttributeClassMemberMethod::set_value(const int &v) {
    if (v < 256) {
        value = v;
    } else {
        throw std::runtime_error("Too large value");
    }
}

2.5.2 Preprocessor Macros

  • Google Style: Avoid defining macros, especially in headers; prefer inline functions, enums, and const variables. Name macros with a project-specific prefix. Do not use macros to define pieces of a C++ API.

  • Simics Style: Appropriately defined macros are fine in Simics. Some macros make it easier for users. For instance, AFTER_CALL simplifies calling an after statement by preventing repeated arguments and reducing errors.

    AFTER_CALL(this, 2.0, &SampleAfter::oneUint64ArgumentClassFunction,
           obj(), one_uint64_);

    Simple macros like #define ONE 1 should be avoided and replaced by inline functions, enums, or const variables.

2.6 Naming

2.6.1 Constant Names

  • Google Style: Use a leading “k” followed by mixed case, like “kDaysInAWeek”.

  • Simics Style: In Simics, constants are named in the same manner as other variables, without requiring any special prefixes or suffixes to indicate they are constants.

2.6.2 Function Names

  • Google Style: Functions should start with a capital letter and have a capital letter for each new word. For example, AddTableEntry.

  • Simics Style Modification: Functions should start with a lower-case letter and have a capital letter for each new word. For example, addTableEntry.

2.6.3 Exceptions to Naming Rules

The Simics API is implemented in C, and as such, it follows a distinct naming convention for functions, classes, and objects. When writing C++ code that interacts closely with the Simics C API, it is advisable to adhere to the existing Simics C naming conventions.

2.7 Comments

In general, follow Google style to use either the // or /* */ syntax. However, if the comments need to be included in the Doxygen output, then the style for that is using the /// or /** **/ syntax.

2.8 Formatting

  • Google Style: To help you format code correctly, we’ve created a settings file for emacs.

  • Simics Style Modification: No public setting file is provided. Internally we used Emacs Lisp files.

2.8.1 Spaces vs. Tabs

  • Google Style: Use only spaces, and indent 2 spaces at a time.

  • Simics Style Modification: Use only spaces for indentation. The indentation width is 4 spaces (not 2). This applies to all indented blocks: functions, classes, control structures, etc.

2.8.2 Line Length

Keep lines to a maximum of 80 characters. This improves readability and helps with code reviews. When a line would exceed 80 characters, break it logically:

// Good: Line breaks at 80 chars
bool isValid = checkConditionOne()
               && checkConditionTwo()
               && checkConditionThree();

// Good: Function call broken into multiple lines
installEventHandler(obj, "event_name",
                    &Callback::handleEvent,
                    objPtr);

2.8.3 Trailing Whitespace

Never include trailing whitespace at the end of lines. Remove any spaces or tabs that appear after the last non-whitespace character.

2.8.4 Inline Comments

When adding inline comments (comments at the end of a line), use at least 2 spaces before the comment marker. This improves visual separation between code and comments:

int count = 42;        // Number of items in the batch
bool isActive = true;  // Flag indicating active state

2.8.5 Pointer and Reference Expressions

  • Google Style: When referring to a pointer or reference (variable declarations, definitions, arguments, return types, template parameters, etc.), you may place the space before or after the asterisk/ampersand. The trailing-space style elides the space in some cases (template parameters, etc.).

    // These are fine, space preceding.
char *c;
const std::string &str;
int *GetPointer();
std::vector<char *>

// These are fine, space following (or elided).
char* c;
const std::string& str;
int* GetPointer();
std::vector<char*>  // Note no space between '*' and '>'

  • Simics Style Modification: Space preceding is preferred in the Simics C++ API (e.g., int * ptr, const std::string & ref). Users may use both formats in their own code, but consistency within a file is recommended.

2.8.6 Boolean Expressions

  • Google Style: The && (logical AND) operators appear at the end of the line. This style is more common in Google code, though placing operators at the beginning of the next line is also acceptable.

    if (this_one_thing > this_other_thing &&
    a_third_thing == a_fourth_thing &&
    yet_another && last_one) {
     ...
}

  • Simics Style Modification: The && (logical AND) operators should appear at the beginning of the next line. This improves readability and makes conditions easier to scan.

    if (this_one_thing > this_other_thing
    && a_third_thing == a_fourth_thing
    && yet_another && last_one) {
     ...
}

2.8.7 Constructor Initializer Lists

  • Google Style: Constructor initializer lists can be all on one line or with subsequent lines indented four spaces. Multiple acceptable formats exist for initializer lists:

    // If the signature and initializer list are not all on one line,
// you must wrap before the colon and indent 4 spaces:
MyClass::MyClass(int var)
    : some_var_(var), some_other_var_(var + 1) {
  DoSomething();
}

// When the list spans multiple lines, put each member on its own line
// and align them:
MyClass::MyClass(int var)
    : some_var_(var),             // 4 space indent
      some_other_var_(var + 1) {  // lined up
  DoSomething();
}

  • Simics Style: Use 8-space indentation (4 spaces doubled) as described in Spaces vs. Tabs. Optionally, users may place the comma (“,”) at the beginning of continuation lines for improved readability.

    // If the signature and initializer list are not all on one line,
// you must wrap before the colon and indent 4 spaces:
MyClass::MyClass(int var)
        : some_var_(var), some_other_var_(var + 1) {
    DoSomething();
}

// When the list spans multiple lines, put each member on its own line
// and align them:
MyClass::MyClass(int var)
        : some_var_(var)              // 8 space indent
        , some_other_var_(var + 1) {  // lined up
    DoSomething();
}
