4 Comments

4.1 Comment formatting

  • CF1 Prefer // comments over /* */ comments, but both are allowed.

  • CF2 Really short comments can be winged (placed on the same line as the code). Preferably leave at least two spaces between the code and the start of the comment.

  • CF3 If a winged comment gets too long to fit, put it on its own line, before the line it is commenting. Indent comments (if not winged) to the same level as surrounding code.

  • CF4 Write multi-line comments as follows, without any empty comment lines.

    // This is a long comment
// that consists of multiple lines

  • CF5 Do not use a comment style other than these mentioned other than in very special circumstances. In particular, do not use banners, boxes or horizontal/vertical lines of characters. These just take up space for no good reason, and grab attention that is better directed to code.

  • CF6 Consider comments to be statements for brace purposes. That is, this if-statement needs braces as if the comment had been a statement.

    if (drunk(user)) {
        // sober up
        drink(user, strong_coffee);
}

  • CF7 Add // at the very beginning of lines in a region to disable the code.

  • CF8 Do not check in disabled code without a very good reason for doing so and a comment stating why it is there. Lacking this, disabled code is fair game for removal without prior notice.

These rules are for visual consistency, to make it easier to locate, read and edit comments.

4.2 Contents of Comments

  • CC1 Comments should only contain information that cannot be easily inferred from the code. If the code is obvious enough, no comment is needed. If not, it is better to spend effort on making the code clearer than explaining it in a comment.

    Example of a bad comment:

    // Flush page cache.
flush_page_cache(cpu);

  • CC2 Explain why, not what. Reading the code gives you what, but not always why. Reasons for a particular design choice are much more useful to the reader. Do not sign comments with name or date.

  • CC3 Do not keep history in comments. They should describe the code as it is, not as it has been. Erase anything that is no longer valid.

    Examples of bad comments:

    // moved here from processor.c

local double delta;   // no longer an integer

// (mike) this is only safe if x != 0

// 980325 rewritten to use new event code

  • CC4 When editing existing code, you are just as responsible for editing the comments that refer to that code so that they are still valid. Incorrect comments should not be left in the code; it is better to remove them if they cannot be updated to reflect the state of the code.

  • CC5 Partly for this reason, it is desirable to keep comments as close as possible to the code they are commenting on. This makes them harder to miss when changing the code. (Do not overdo this and fragment the code with too many interspersed comments—try to strike a balance.)

  • CC6 TODO and FIXME comments should make it clear what needs to be done or fixed, and why; otherwise they contain no information.

    Refer to Bugzilla bug numbers in comments if the issue is still open. When fixed, such references should be removed. Example:

    // FIXME: This is incorrect if p==0. (bug #4711)

  • CC7 Prefer describing data to explaining code. If the data structures are known, the code manipulating them should be natural and need little extra explanation.

  • CC8 Keep winged and one-line comments terse and telegraphic in style, in order to keep their widths down. Cut down on articles and punctuation.

    Bad:      t += dt;     // Compensate for the time skew.
Good:     t += dt;     // compensate for time skew

4.3 File comments

  • FC1 Comments at the beginning of source code may contain a brief description of the file if not evident. Ordinary comment rules apply. If copyright and license statements are required, they should also be added to the top comment section.
  • FC2 Other than this, keep file comments to an absolute minimum, in accordance with the general comment principles above.
