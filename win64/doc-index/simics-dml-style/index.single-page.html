Style Guide for DML

This is a short summary of the programming style for programming in DML. Both syntactic issues and general language usages are covered.

1 Document level

The rules below are recommendations which are there to be followed. They need not be obeyed by the letter all the time, since there will always be exceptions and nobody should be the slave under rigid rules.

However, you should be prepared to justify every deviation from the rules. Their purpose is to make code easier to maintain for the programmer collective. Breaking them in a way that makes it harder for others is both unprofessional and egotistic.

Changes to this document should not take place without prior consultation of those affected by the change. They should also be informed about changes afterwards.

2 Language

This document covers DML only. Where applicable, the rules are similar to the rules for C, specified in another document.

3 General syntax

The DML style is based on the Kernighan & Ritchie C style with 4 steps indentation. Spaces are used, not tabs. Braces are put on the same line as the keyword. Details are listed below.

3.1 Spacing

Put whitespace (space or newline):

  • SP.reserved around reserved words, such as if, else, default, size, const and in, except when a reserved word is used as an identifier (e.g., local uint8 *data;)
  • SP.braces around braces ({ and })
  • SP.binop around binary operators except the dereferencing operators dot (a.b) and arrow (a->b)
  • SP.ternary around ? and : in the ternary ?: operator
  • SP.punct after but not before colon, semicolon and comma
  • SP.ptrdecl between a type and the * marking a pointer
  • SP.comment around the comment delimiters //, /* and **/

There should be no space:

  • NSP.funpar between a function/method name and its opening parenthesis
  • NSP.inparen immediately inside parentheses or brackets
  • NSP.unary between a unary operator and its operand, including the $ marking a reference in the object namespace
  • NSP.ptrdecl after the * marking a pointer in a declaration

3.2 Indentation

  • IN1 Lines are indented four spaces for each indentation level.

  • IN2 Tab characters (ASCII 9) should never be used to indent lines.

  • IN3 If the previous line contains an opening brace without corresponding closing brace, the current line should be indented one level more than the previous line.

  • IN4 A closing brace at the beginning of a line is indented one level less than the previous line. A closing brace should only ever appear on the same line as the opening brace or first on a line.

  • IN5 A continuation line that is broken inside a parenthesized expression is indented to line up inside the corresponding parenthesis on the previous line.

    x = interrupt_disabled || is_intr(interrupt_device,
                                  irq_level);

  • IN6 A continuation line not broken inside a parenthesized expression is indented one level.

    interrupt_enabled =
    irq_enabled(interrupt_device);

  • IN7 Any line not indented according to the rules above is indented to same level as the preceding non-empty line.

  • IN9 Case labels are indented one level less than surrounding lines, so that they are on the same level as the switch statement. The same applies to goto labels, but keep an indentation of at least one space, to avoid mistaking them for top-level definitions.

    method bonus(player_t *p) -> (int b) {
    b = 0;
    switch (p->what) {
    case Winning:
        b = 1000;
        goto mystery;
    case Losing:
        b = -1000; break;
    }
    return;
 mystery:
    b += random() % 500;
}

  • IN10 When the body of a while or for loop is left empty, indent the semicolon to the appropriate statement level.

    for (s = 0; (1 << s) < x; s++)
        ;

3.3 Braces

  • BR1 No braces are required around single-statement blocks (but see the rule for comments).

    if (count == 0)
    empty = true;

  • BR2 Empty DML object declarations should be written with a semicolon instead of an empty brace pair

    register reg1;         // GOOD
register reg2 {        // BAD
}

  • BR3 Methods should have the opening brace on the same line as the method declaration.

    method set(uint32 value) {
    ...
}

3.4 Line Length and Breaking

  • LL1 Lines should be kept shorter than 80 characters. Longer lines wrap or become partially invisible in editors whose windows have the standard width of 80 columns, which makes the code much harder to read.

    Having longer lines than the width of the screen (editor window) is unacceptable since it makes it much harder to read and completely destroys any structure given by indentation. Most lines are short, so forcing all programmers to have an editor window wide enough for a minority of lines wastes screen space, or forces people to use a smaller font that is harder on the eyes, especially for programmers without perfect eyesight.

    A window width of 80 columns is as close to standard as can be found anywhere, being used by many terminals and terminal emulators. It also matches normal width used by text printing software, which is important for printing source code for inspection. Additionally, printed text rarely has longer lines than this since it makes them harder to read. Finally, lines exactly 80 characters long are undesirable since they often wrap around in editors.

    Excessive indentation gives less room to write code without exceeding the line length limit. To avoid this in good coding style, you can:

    • use continue, break or return to bypass code rather than putting code inside the body of a conditional
    • factor out code into methods, which often improves legibility and sometimes speed as well

  • LL2 Break long lines before binary operators, not after

    x = (a_very_long_expression
     + another_very_long_expression)
    * a_third_long_expression;

    This clearly indicates that a line continues an expression, and it is also consistent with several other standard styles. It also makes the operator easier to recognize, and is more in line with the familiar prefix notation used by function calls.

  • LL3 Break conditional expressions before the ?, or both before the ? and before the :.

    harvest_resource(my->gas < GAS_THRESHOLD
                 ? Rsrc_Gas
                 : (my->minerals < MINERAL_THRESHOLD
                    ? Rsrc_Minerals : nearest_resource()));

  • LL4 Following lines should be indented at their natural position, as shown above. Add parentheses if it makes indenting easier. You may also add spaces in expressions if you really want them to line up

    if (   (flags & 0x86000001) == 0x84000001
    || (flags & 0xfc000003) == 0x38000002
    || (flags & 0x0000003f) == 0x0000001b)
        ...

  • LL5 Break long method declarations with output parameters before the arrow.

    method inquiry_status(uint64 physical_address)
    -> (uint16 status) {
    ...
}

  • LL6 Function and method invocations can be broken after the opening parenthesis, with the continuation lines indented one level.

    signal_interface *my_interface = SIM_get_interface(
    other_object, SIGNAL_INTERFACE);

3.5 Parentheses

  • PA1 Parentheses not required by the language may be added to expressions for clarity or indentation.

  • PA2 Parentheses should be added when the operator precedence is not intuitively obvious. This is mandatory to resolve precedence between the following operators, even if it is well-defined by the language

    • || vs &&
    • bitwise operators (|, &, ^) vs each other
    • bitwise operators vs arithmetic operators (+, -, *, /, %)
    • bitwise operators vs comparisons (==, !=, >, <, >=, <=)
    • shift operators (<<, >>) vs arithmetic operators
    • comparisons vs each other
    • shift operators vs each other

  • PA3 When neither language nor understanding or layout require parentheses, they should be omitted.

  • PA4 Parentheses should also be added to assignment statements inside expressions, to clearly show that they were intended.

DML inherits its operator precedence rules from C, which unfortunately includes some defects for historical reasons; also, while it may be obvious to a hardware engineer that & has higher precedence than |, it is not linguistically obvious. Superfluous parentheses often make the code harder to read for a programmer who is familiar with the language, and may give false hints that something unusual is going on.

4 Comments

4.1 Comment formatting

  • CF1 Prefer // comments over /* */ comments, but both are allowed.

  • CF2 Really short comments can be winged (placed on the same line as the code). Preferably leave at least two spaces between the code and the start of the comment.

  • CF3 If a winged comment gets too long to fit, put it on its own line, before the line it is commenting. Indent comments (if not winged) to the same level as surrounding code.

  • CF4 Write multi-line comments as follows, without any empty comment lines.

    // This is a long comment
// that consists of multiple lines

  • CF5 Do not use a comment style other than these mentioned other than in very special circumstances. In particular, do not use banners, boxes or horizontal/vertical lines of characters. These just take up space for no good reason, and grab attention that is better directed to code.

  • CF6 Consider comments to be statements for brace purposes. That is, this if-statement needs braces as if the comment had been a statement.

    if (drunk(user)) {
        // sober up
        drink(user, strong_coffee);
}

  • CF7 Add // at the very beginning of lines in a region to disable the code.

  • CF8 Do not check in disabled code without a very good reason for doing so and a comment stating why it is there. Lacking this, disabled code is fair game for removal without prior notice.

These rules are for visual consistency, to make it easier to locate, read and edit comments.

4.2 Contents of Comments

  • CC1 Comments should only contain information that cannot be easily inferred from the code. If the code is obvious enough, no comment is needed. If not, it is better to spend effort on making the code clearer than explaining it in a comment.

    Example of a bad comment:

    // Flush page cache.
flush_page_cache(cpu);

  • CC2 Explain why, not what. Reading the code gives you what, but not always why. Reasons for a particular design choice are much more useful to the reader. Do not sign comments with name or date.

  • CC3 Do not keep history in comments. They should describe the code as it is, not as it has been. Erase anything that is no longer valid.

    Examples of bad comments:

    // moved here from processor.c

local double delta;   // no longer an integer

// (mike) this is only safe if x != 0

// 980325 rewritten to use new event code

  • CC4 When editing existing code, you are just as responsible for editing the comments that refer to that code so that they are still valid. Incorrect comments should not be left in the code; it is better to remove them if they cannot be updated to reflect the state of the code.

  • CC5 Partly for this reason, it is desirable to keep comments as close as possible to the code they are commenting on. This makes them harder to miss when changing the code. (Do not overdo this and fragment the code with too many interspersed comments—try to strike a balance.)

  • CC6 TODO and FIXME comments should make it clear what needs to be done or fixed, and why; otherwise they contain no information.

    Refer to Bugzilla bug numbers in comments if the issue is still open. When fixed, such references should be removed. Example:

    // FIXME: This is incorrect if p==0. (bug #4711)

  • CC7 Prefer describing data to explaining code. If the data structures are known, the code manipulating them should be natural and need little extra explanation.

  • CC8 Keep winged and one-line comments terse and telegraphic in style, in order to keep their widths down. Cut down on articles and punctuation.

    Bad:      t += dt;     // Compensate for the time skew.
Good:     t += dt;     // compensate for time skew

4.3 File comments

  • FC1 Comments at the beginning of source code may contain a brief description of the file if not evident. Ordinary comment rules apply. If copyright and license statements are required, they should also be added to the top comment section.
  • FC2 Other than this, keep file comments to an absolute minimum, in accordance with the general comment principles above.

5 Naming

  • NN1 In absence of other rules, identifiers are written in lower case letters, words separated by underscores.

  • NN2 Do not append a number as a general method to create new identifiers, other than in very special circumstances.

    method draw_line(int x1, int y1, int x2, int y2) // GOOD
method invalidate_object2(conf_object_t *obj)    // BAD

5.1 Method names

  • NM1 Methods that are executed primarily for their side-effect should be named after what they do. Methods executed for their return value should be named after what they return. If the method is a predicate (returning a boolean value), it should be named after the condition when it returns a true value.

    method raise_interrupt(uint8 level)
method current_irq_level() -> (float power)
method is_enabled(int x) -> (bool enabled)

5.2 Variable and device object names

  • NV1 Variables should be named after what they contain, not from the variable or its type. The more local a variable is, the shorter can be its name. Use long, descriptive names for top-level names; use short names in local scopes. Names more frequently used can also be shorter.
  • NV2 In particular, do not use tmp or ptr in identifiers; it is rare that it is needed to point out that a variable contains a temporary value or a pointer.
  • NV3 Do not prefix names with an article, such as an_object or the_score.

5.3 Type names

  • NT1 Typedef names should end in _t. Typedef structs unless only used locally.

5.4 File names

  • NF1 In file names, words are separated by hyphens rather than underscores.

6 Types

  • TY1 Where possible, make struct definitions private to code if other parts of the source only need to handle pointers to the struct.
  • TY2 Avoid casts whenever possible, since this can hide errors while suppressing warnings.
  • TY3 Do not cast pointers to/from (void *)
  • TY4 Use intermediate variables to convert a (void *) to a specific pointer.
  • TY5 Take the address of substructures instead of casting struct pointers.

Examples:

local void *p = ...
local int strength = cast(p, (troll_t *))->strength;  // BAD

local troll_t *t = p;
local int strength = t->strength;                     // GOOD

save_object(cast(cpu, (conf_object_t *)));      // BAD
save_object(&cpu->log.obj);                     // GOOD

local uint32 k = get_key();

7 Various issues

  • VI1 Avoid assignments inside expressions, unless needed for flow control reasons

    if ((err = hurt_enemy(e)) < 0) ...           // BAD

err = hurt_enemy(e);
if (err < 0) ...                             // GOOD

while ((victim = next_target()) != NULL) ... // GOOD

    This makes the expressions simpler to analyze and immediately understand; side-effects require some further thought. It also saves on parentheses and line length.

  • VI2 When comparing an expression against a constant, put the constant last

    if (2 == x) ...              // BAD
if (x == 2) ...              // GOOD

    This is more intuitive and scans better, since it corresponds more closely to how you would pronounce it in natural language (“if x is equal to two”, never “if two is equal to x”, since “two” is not likely to change.)

7.1 Switch statements

  • SW1 Always indicate a switch case fall-through with a comment.

    switch (monster->state) {
case Sleeping:
        wake_up(monster);
        // FALLTHROUGH
case Awake:
        attack(monster, player);
        break;
case Dead:
        rattle_bones(monster->corpse);
        break;
}

  • SW2 All other cases should have a break statement, even the last case in the switch, unless they use a return/continue/goto to transfer control elsewhere.

8 Editor Support

Included in the Simics distribution are Emacs and Vim editing modes for DML. For Emacs, add the code below to your .emacs file to automatically use it when editing DML, but change the path to your Simics installation:

(setq load-path (cons "/simics-install-dir/scripts" load-path))
(autoload 'dml-mode "dml-mode" "DML mode" t)
(add-to-list 'auto-mode-alist '("\\.dml$" . dml-mode))

(c-add-style "dml"
             '((comment-column . 45)
               (c-basic-offset . 4)
               (c-offsets-alist . ((substatement-open . 0)
                                   (topmost-intro-cont . +)))
               (c-block-comment-prefix . "")
               (indent-tabs-mode . nil)))

(setq c-default-style (cons '(dml-mode . "dml")
                             c-default-style))

For Vim, copy the following lines to your .vimrc, but change the path to your Simics installation:

au BufRead,BufNewFile *.dml set filetype=dmllang
au! Syntax dmllang source /simics-install-dir/scripts/dml.vim
