SystemC Checkpoint Library Manual

1 Introduction

The SystemC Checkpoint Library provides the capability to save and restore the state of SystemC devices. Using the API, users can add checkpoint support to their devices. C++ and SystemC data types, user-defined data types, pointers, generic payloads, and STL containers can be saved in checkpoints.

The library also provides infrastructure for state keepers. This is useful when applications need to handle parts of device state separately, for example for large memory images.

The checkpoint library is integrated into the Simics SystemC Library, which makes save and restore of SystemC state analogous to the rest of Simics. The checkpoint library can also be used independently of Simics.

This manual describes how to use the checkpoint library to serialize SystemC modules and other user types.

2 Concept Overview

The checkpoint API relies on the Boost C++ Libraries, specifically the Boost.Serialization library. To maintain a clear separation between Boost and the Checkpoint library the Serialization library has been forked into the cci:: namespace.

2.1 Serializers

Classes that contain state should implement a serialize function. This function is invoked when checkpoints are saved or loaded and should serialize all state within the class. Any subsequent objects contained within the class may in turn be serialized by invoking their serialize function.

SystemC modules are serialized by the checkpoint library itself. The code that provides a module is responsible for instantiating a Serializer, which registers that module type with the framework so that it may be automatically serialized. That is, a library providing modules is responsible for registering those modules, and a programmer creating a new module is responsible for registering it with the checkpoint library.

This is described in detail in the Serialization section.

Reference snippets:

SC_MODULE(UserModule) {
  public:
    SC_CTOR(UserModule) : a_(0), b_(0) {}

  private:
    int a_;
    int b_;

    friend class cci::serialization::access;
    template <class Archive>
        void serialize(Archive& ar, const unsigned int version) {
        ar & SMD(a_);
        ar & SMD(b_);
    }
};

static sc_checkpoint::serialization::Serializer<UserModule> um_serializer;

2.2 Non-modules

Types that are not SystemC modules must be explicitly serialized in the parent class serialize function. These types do not need a Serializer instance.

The user does not have to provide serialize functions for all types, however. For instance, C++ data types are supported by Boost.Serialization out-of-the-box. Furthermore, the checkpoint library provides serialization support for some SystemC types and STL containers.

See the Serialization section for details.

Reference snippet:

SC_MODULE(A) {
  public:
    SC_CTOR(A) : a_(0) {}
    int a_;

    template <class Archive>
    void serialize(Archive& ar, const unsigned int version) {
        ar & SMD(a_);
    }
};

class B {
  public:
    B() : b_(0) {}
    int b_;

    template <class Archive>
    void serialize(Archive& ar, const unsigned int version) {
        ar & SMD(b_);
    }
};

SC_MODULE(C) {
  public:
    SC_CTOR(C) : a_("a") {}
    A a_;
    B b_;

    template <class Archive>
    void serialize(Archive& ar, const unsigned int version) {
        // no need to explicitly serialize a_ since it is a module
        ar & SMD(b_);
    }
};

static sc_checkpoint::serialization::Serializer<A> a_serializer;
// there is no serializer for 'B'
static sc_checkpoint::serialization::Serializer<C> c_serializer;

2.3 State Keepers

State keepers let users handle saving and restoration for parts of their system, which is useful for large memory images and incremental checkpoints.

All SystemC objects implementing the state-keeper interface are discovered automatically. There is no need to register a serialize function for these objects. Instead, the methods in the state-keeper interface are used for checkpoint handling.

This is detailed in the State Keeper Interface section.

Reference snippet:

class StateKeeperInterface {
  public:
    virtual ~StateKeeperInterface() {}

    /**
     * State in the implementer is saved incrementally using this function. The
     * function must produce a handle which the library can use to restore or
     * merge with other in-memory states.
     */
    virtual bool save(void **handleOut) = 0;

    /**
     * Arbitrary state is restored in the implementer when this function is
     * invoked with a corresponding handle.
     */
    virtual bool restore(void *handle) = 0;

    /**
     * This function merges two states that are identified by the handles. The
     * contents of handleRemove are appended to handlePrevious, and
     * handleRemove is subsequently removed rendering the handle invalid.
     * NOTE: handlePrevious could be NULL, in which case handleRemove is just
     * removed
     */
    virtual bool merge(void *handlePrevious, void *handleRemove) = 0;

    /**
     * Write the state to disk. Dir is the directory in which state shall be
     * saved and prefix is a directory unique identifier. Persistent is a
     * boolean that indicates whether or not only persistent state should be
     * saved to disk. If persistent is not set all state is saved.
     */
    virtual bool write(const std::string &dir,
                       const std::string &prefix,
                       bool persistent) = 0;

    /**
     * Write a standalone checkpoint to disk. That is, the written checkpoint
     * cannot be dependent on any previous checkpoints. Dir is the directory in
     * which state shall be saved and prefix is a directory unique
     * identifier. Persistent is a boolean that indicates whether or not only
     * persistent state should be saved to disk. If persistent is not set all

     * state is saved.
     */
    virtual bool write_standalone(
        const std::string &dir, const std::string &prefix, bool persistent) = 0;

    /**
     * Restore state from disk. Dirs is a list of checkpoint directories and
     * prefix is an identifier.
     */
    virtual bool read(const std::vector<std::string> &dirs,
                      const std::string prefix, bool persistent) = 0;
};

2.4 Threads

The checkpoint library does not save and restore thread stacks directly. It provides the means to restart threads and restore the corresponding thread stacks. This is accomplished by a combination of using the serialize function of the parent module to restore the state of the thread and a following reset of the thread process. The checkpoint library guarantees that all serialize functions are called before threads are restarted.

See the Thread Stack Restore section for details.

Reference snippet:

SC_MODULE(ThreadModule) {
    enum {
        WAIT_FOR_EVENT,
        WAIT_FOR_TIME,
        DONE
    };
    SC_CTOR(ThreadModule) : state_(WAIT_FOR_EVENT) {
        SC_THREAD(thread);
    }
    template <class Archive>
        void serialize(Archive& ar, const unsigned int version) {
        ar & SMD(state_);
    }
    void thread() {
        while (true) {
            switch (state_) {
            case WAIT_FOR_EVENT: {
                sc_core::wait(event_);
                state_ = WAIT_FOR_TIME;
            }
                break;
            case WAIT_FOR_TIME: {
                sc_core::wait(5, sc_core::SC_PS);
                state_ = DONE;
            }
                break;
            case DONE: {
                sc_core::wait();
            }
                break;
            }
        }
    }

    sc_core::sc_event event_;
    int state_;
};

2.5 Payloads

The checkpoint library also provides infrastructure for the restoration of generic payloads. In order to restore payloads, the objects that reference them must serialize them as part of their serialize functions, and a PayloadUpdate object should be provided to restore the contents of the payload.

This is described in the Serializing Generic Payloads section.

Reference snippets:

template <class T>
class PayloadUpdate : public PayloadUpdateInterface {
  public:
    PayloadUpdate() {
        PayloadUpdateRegistry::Instance()->registerUpdater(this);
    }
    virtual ~PayloadUpdate() {
        PayloadUpdateRegistry::Instance()->unregisterUpdater(this);
    }

    virtual void set_data_ptr(T *t, tlm::tlm_generic_payload *payload) {}
    virtual void set_byte_enable_ptr(T *t,
                                     tlm::tlm_generic_payload *payload) {}
    virtual void set_extensions(T *t, tlm::tlm_generic_payload *payload) {}
    virtual void set_memory_manager(T *t, tlm::tlm_generic_payload *payload) {}

  private:
    virtual bool isUpdatable(sc_core::sc_object *object) {
        return dynamic_cast<T *> (object) != NULL;
    }
    virtual void updateDataPtr(sc_core::sc_object *object,
                               tlm::tlm_generic_payload *payload) {
        set_data_ptr(static_cast<T *>(object), payload);
    }
    virtual void updateByteEnablePtr(sc_core::sc_object *object,
                                     tlm::tlm_generic_payload *payload) {
        set_byte_enable_ptr(static_cast<T *>(object), payload);
    }
    virtual void updateExtensions(sc_core::sc_object *object,
                                  tlm::tlm_generic_payload *payload) {
        set_extensions(static_cast<T *>(object), payload);
    }
    virtual void updateMemoryManager(sc_core::sc_object *object,
                                     tlm::tlm_generic_payload *payload) {
        set_memory_manager(static_cast<T *>(object), payload);
    }
};

SC_MODULE(PayloadModule) {
  public:
    SC_CTOR(PayloadModule) {
        payload_ = new tlm::tlm_generic_payload;
    }
    template <class Archive>
    void serialize(Archive& ar, const unsigned int version) {
        ar & SMD(data_)
           & SMD(payload_);
    }

    unsigned char data_[10];
    tlm::tlm_generic_payload *payload_;
};

class PayloadUpdater : public sc_checkpoint::PayloadUpdate<PayloadModule> {
  public:
    PayloadUpdater() {}
    virtual void set_data_ptr(PayloadModule *m,
                              tlm::tlm_generic_payload *p) {
        p->set_data_ptr(m->data_);
    }
};

static sc_checkpoint::serialization::Serializer<PayloadModule> p_serializer;
static PayloadUpdater p_updater;

3 Serialization

To interact with Boost.Serialization, the checkpoint library provides a custom archive and a set of macros/functions used to transform state to and from text.

The checkpoint library serializes SystemC state and formats output as JSON text. Only state is saved and restored. Configuration recreation is the user’s responsibility.

3.1 Serializing User Types

Classes that should be serialized implement a serialize function.

Use the SMD macro to capture serializable metadata from variables. Use create_smd when you want explicit naming for compatibility over time. This is recommended for backwards compatibility when the contents otherwise wrapped in SMD are likely to change.

Do not serialize the same instance multiple times; behavior is undefined.

For advanced Boost.Serialization patterns (split save/load, external serialize, and so on), see the Boost.Serialization documentation.

Reference snippets:

template <class Archive>
void serialize(Archive& ar, const unsigned int version) {
    ar & SMD(static_array_);
}

template<class Archive>
void save(Archive &ar, const unsigned int version) const {
    ar << SMD(size_)
       << sc_checkpoint::serialization::create_smd(
              "array", sc_checkpoint::serialization::make_array(array_, size_));
}

template<class Archive>
void load(Archive &ar, const unsigned int version) {
    delete[] array_;
    ar >> SMD(size_);

    array_ = new int[size_];
    ar >> sc_checkpoint::serialization::create_smd(
              "array", sc_checkpoint::serialization::make_array(array_, size_));
}

CCI_SERIALIZATION_SPLIT_MEMBER()

3.2 Type Registration

When modules implement serialize, register them by creating a matching Serializer<T> instance. This is done on a class-by-class basis; it is not necessary to instantiate a Serializer for every class instance.

Only module types need Serializer registration. Supporting non-module types need only implement serialize and be archived by containing modules. If a third-party library provides checkpointable modules, that library is responsible for creating the necessary Serializer instances.

Reference snippet:

static sc_checkpoint::serialization::Serializer<UserModule> um_serializer;

4 State Keeper Interface

State keepers are useful when full-image save/restore is too expensive and incremental state handling is needed.

StateKeeperInterface includes methods for in-memory checkpoints (save, load, merge) and on-disk checkpoints (write_standalone, write, read).

All methods report success/failure through their return value.

Reference snippet:

class StateKeeperInterface {
  public:
    virtual ~StateKeeperInterface() {}

    /**
     * State in the implementer is saved incrementally using this function. The
     * function must produce a handle which the library can use to restore or
     * merge with other in-memory states.
     */
    virtual bool save(void **handleOut) = 0;

    /**
     * Arbitrary state is restored in the implementer when this function is
     * invoked with a corresponding handle.
     */
    virtual bool restore(void *handle) = 0;

    /**
     * This function merges two states that are identified by the handles. The
     * contents of handleRemove are appended to handlePrevious, and
     * handleRemove is subsequently removed rendering the handle invalid.
     * NOTE: handlePrevious could be NULL, in which case handleRemove is just
     * removed
     */
    virtual bool merge(void *handlePrevious, void *handleRemove) = 0;

    /**
     * Write the state to disk. Dir is the directory in which state shall be
     * saved and prefix is a directory unique identifier. Persistent is a
     * boolean that indicates whether or not only persistent state should be
     * saved to disk. If persistent is not set all state is saved.
     */
    virtual bool write(const std::string &dir,
                       const std::string &prefix,
                       bool persistent) = 0;

    /**
     * Write a standalone checkpoint to disk. That is, the written checkpoint
     * cannot be dependent on any previous checkpoints. Dir is the directory in
     * which state shall be saved and prefix is a directory unique
     * identifier. Persistent is a boolean that indicates whether or not only
     * persistent state should be saved to disk. If persistent is not set all

     * state is saved.
     */
    virtual bool write_standalone(
        const std::string &dir, const std::string &prefix, bool persistent) = 0;

    /**
     * Restore state from disk. Dirs is a list of checkpoint directories and
     * prefix is an identifier.
     */
    virtual bool read(const std::vector<std::string> &dirs,
                      const std::string prefix, bool persistent) = 0;
};

4.1 Maintaining Portability

When writing checkpoints to disk, use relative references rather than absolute paths. If checkpoint directories move, relative references remain valid and can be remapped from the path list provided during read.

5 Thread Stack Restore

Thread stack restoration uses a two-phase process:

  1. Restore serialized state.
  2. Restart thread processes and rebuild stacks.

Thread restart logic must not rely on global synchronization or restart order.

Do not catch sc_unwind_exception. Since it derives from std::exception, avoid broad exception handling that would intercept it.

6 Callbacks

Devices may need pre/post actions during serialization (for cache flushing, thread preparation, and similar work).

Implement SerializeCallbackInterface to receive callback hooks around serialization and before thread startup.

Reference snippet:

class SerializeCallbackInterface {
  public:
    enum State {
        State_Saving = 0x1,
        State_Loading,
        State_Persistent = 0x10,
        State_Saving_Persistent = State_Saving | State_Persistent,
        State_Loading_Persistent = State_Loading | State_Persistent
    };

    virtual ~SerializeCallbackInterface() {}

    /**
     * Invoked before any save/load/serialize function is called and before any
     * state keepers are invoked.
     */
    virtual void pre_serialize_callback(State state) = 0;

    /**
     * Invoked after any save/load/serialize function has been called, but
     * before any threads have been restarted.
     */
    virtual void post_serialize_callback(State state) = 0;
};

7 DMI Handling

Models are responsible for their own memory management. DMI addresses can change between runs, so DMI addresses received before checkpoint restore must be invalidated on load.

8 Checkpoint Control

In standalone applications (without Simics), use CheckpointControl to trigger save/load operations.

Reference snippets:

class InMemoryStateInterface {
  public:
    virtual ~InMemoryStateInterface() {}
    virtual bool save(void **handle) = 0;
    virtual bool restore(void *handle) = 0;
    virtual bool merge(void *handlePrevious, void *handleRemove) = 0;
};

class OnDiskStateInterface {
  public:
    virtual ~OnDiskStateInterface() {}

    virtual bool write(const std::string &dir, bool persistent) = 0;

    virtual bool write_standalone(const std::string &dir, bool persistent) = 0;

    virtual bool read(const std::vector<std::string> &dirs,
                      bool persistent) = 0;
};

9 Limitations

  • Disk checkpoints are not platform-independent between Linux and Windows.
  • Thread stacks are not saved directly; only restart/reconstruction support is provided.
  • Floating-point save/restore may lose precision.
  • Persistent-only state save is not yet supported.
  • Dynamic processes are not supported.
  • Dynamic events are not supported.
  • Checkpoint updaters for old-checkpoint compatibility are not supported.
  • Only the QuickThreads backend is supported.
  • DMI requires explicit model-level invalidation handling.
  • Serializing the same instance multiple times is forbidden.
  • Event ordering indeterminism inside a delta cycle is not corrected.
