Style Guide for C

This is a short summary of the programming style used in Simics for programming in C, but parts are also valid for other languages. Both syntactic issues and general language usages are covered.

1 Document level

The rules below are recommendations which are there to be followed. They need not be obeyed by the letter all the time, since there will always be exceptions and nobody should be the slave under rigid rules.

However, you should be prepared to justify every deviation from the rules. Their purpose is to make code easier to maintain for the programmer collective. Breaking them in a way that makes it harder for others is both unprofessional and egotistic.

Changes to this document should not take place without prior consultation of those affected by the change. They should also be informed about changes afterwards.

2 Language

This document does not cover C++; there is a separate style guide for that language. Older C++ code may be written in a style largely following the C rules, but new code should follow the language-specific style.

The allowed language is ISO C99. Note that some files may have stricter requirements. For instance, many public header files need to work with Microsoft Visual C, which is approximately C89 but allowing //-style comments.

Language extensions should only be used if there is a true benefit from doing so that outweighs the mess caused by conditional compilation to allow the code to build on platforms that do not support the extensions.

String literals should always be considered to have the type const char *, not char *.

Note that on Windows, interface is a reserved word or a preprocessor macro, so it cannot be used as an identifier.

All source code is written in UTF-8 without BOM. Non-ASCII characters may be used in comments and string literals where appropriate.

3 General syntax

The C style is Kernighan & Ritchie with 8 steps indentation. Spaces are used, not tabs. Braces are put on the same line as the keyword.

Put a single space:

  • between if, while, switch and for and their opening parenthesis
  • between else, while and do and nearby braces
  • around binary operators except comma, dot and arrow (->)
  • around ? and :
  • after but not before colon (after goto or switch labels), semicolon and comma
  • around the ## operator if it makes the code clearer
  • between a type and the * marking a pointer

There should be no space:

  • between a function/macro name and its opening parenthesis
  • immediately inside parentheses or brackets
  • between an unary operator (including casts) and its operand
  • after the * marking a pointer in a declaration

Function definitions are written with the function name starting in the leftmost column, so the return type is on the preceding line; this is so it can be easily found by grepping. Function prototypes are written the function name after the return type as usual.

Example:

person_t *godfather(child);

person_t *
father(person_t *child)
{
        if (child->parent[0].sex == Male) {
                if (child->parent[1].sex == Male)
                        return child->parent[random() & 1];
                else
                        return child->parent[0];
        } else {
                if (child->parent[1].sex == Male)
                        return child->parent[1];
                else
                        return godfather(child);
        }
}

Case labels are outdented 8 spaces relative the current level, so that they are on the same level as the switch statement. The same applies to goto labels, but keep an indentation of at least one space, to avoid mistaking them for top-level definitions.

Example:

int
bonus(player_t *p)
{
        int b = 0;
        switch (p->what) {
        case Winning:
                b = 1000;
                goto mystery;
        case Losing:
                b = -1000; break;
        }
        return b;
 mystery:
        b += random() % 500;
        return b;
}

No braces are required around single-statement blocks (but see the rule for comments in section 4.1).

If one or more branches of an “if-else” statement require braces, then all branches should be wrapped inside braces.

if (check(value)) {
        apply(value);
        return 0;
} else  /* BAD */
        return -1;

if (check(value)) {
        apply(value);
        return 0;
} else {  /* GOOD */
        return -1;
}

When the body of a while or for loop is left empty, indent the semicolon to the appropriate statement level:

for (s = 0; (1 << s) < x; s++)
        ;

A very common style which yields dense yet readable code. 8 steps indentation is common as well and gives very good separation of levels but may lead to excessive indentation; changing indentation width would be a major source code change.

3.1 Line length and breaking

Lines should be kept shorter than 80 characters. Longer lines wrap or become partially invisible in editors whose windows have the standard width of 80 columns, which makes the code much harder to read.

Having longer lines than the width of the screen (editor window) is unacceptable since it makes it much harder to read and completely destroys any structure given by indentation. Most lines are short, so forcing all programmers to have an editor window wide enough for a minority of lines wastes screen space, or forces people to use a smaller font that is harder on the eyes, especially for programmers without perfect eyesight.

A window width of 80 columns is as close to standard as can be found anywhere, being used by many terminals and terminal emulators. It also matches normal width used by text printing software, which is important for printing source code for inspection. Additionally, printed text rarely has longer lines than this since it would make them harder to read. Finally, lines exactly 80 characters long are undesirable since they often wrap around in editors.

Excessive indentation gives less room to write code without exceeding the line length limit. To avoid this in good coding style, you can:

  • use continue, break or return to bypass code rather than putting code inside the body of a conditional
  • factor out code into functions (possibly declared inline), which often improves legibility and sometimes speed as well
  • only indent the first level of C code inside SimGen files one step (8 spaces)

Break long lines before binary operators, not after:

x = (a_very_long_expression
     + another_very_long_expression)
    * a_third_long_expression;

This clearly indicates that a line continues an expression, and it is also consistent with several other standard styles. It also makes the operator easier to recognize, and is more in line with the familiar prefix notation used by function calls.

Break conditional expressions before the ?, or both before the ? and before the :. Example:

harvest_resource(my->gas < GAS_THRESHOLD
                 ? Rsrc_Gas
                 : (my->minerals < MINERAL_THRESHOLD
                    ? Rsrc_Minerals : nearest_resource()));

Following lines should be indented at their natural position, as shown above. Add parentheses if it makes indenting easier.

Alternatively, conditional expressions may be structured in a chained fashion:

printf("Good %s!",
       hour < 12 ? "morning"
       : hour < 18 ? "afternoon"
       : hour < 22 ? "evening"
       : "night");

The conditions may be put inside round brackets if that improves readability.

You may also add spaces in expressions if you really want them to line up:

if (   (flags & 0x86000001) == 0x84000001
    || (flags & 0xfc000003) == 0x38000002
    || (flags & 0x0000003f) == 0x0000001b)
        ...

Long strings should be broken before a space between words, not after:

const char *letter = "Dear John,\n\tI did not want to write this"
                     " letter but I cannot live with you any"
                     " longer. You can keep the elephant and the"
                     " zebra, but the giant squid is mine! MINE!";

This makes the spaces easier to find, and to prevent missing spaces where the strings are broken up.

3.2 Parentheses

Parentheses not required by the language may be added to expressions for clarity or indentation.

Parentheses should be added when the operator precedence is not intuitively obvious. This is mandatory to resolve precedence between the following operators, even if it is well-defined by the language:

  • || vs &&
  • bitwise operators (|, &, ^) vs each other
  • bitwise operators vs arithmetic operators (+, -, *, /, %)
  • bitwise operators vs comparisons (==, !=, >, <, >=, <=)
  • shift operators (<<, >>) vs arithmetic operators
  • comparisons vs each other
  • shift operators vs each other

When neither language nor understanding or layout require parentheses, they should be omitted.

C has some defects in its operator precedence rules for historical reasons; also, while it may be obvious to a hardware engineer that & has higher precedence than |, it is not linguistically obvious. Gcc kindly warns in some but not all of these cases. Superfluous parentheses often make the code harder to read for a programmer who is familiar with the language, and may give false hints that something unusual is going on.

Parentheses should also be added to assignment statements inside expressions, to clearly show that they were intended.

Do not put parentheses around the sizeof operand when it is an expression:

int_size = sizeof(int);    // int is a type.
x_size = sizeof x;         // x is an expression.

4 Comments

4.1 Comment formatting

Really short comments can be winged (placed on the same line as the code). Leave at least two spaces between the code and the start of the comment.

If a winged comment gets too long to fit, put it on the previous line. Indent short comments (if not winged) to the same level as surrounding code.

Write multi-line comments as follows:

/*
 * This is a long comment
 * that consists of multiple lines
 */

That is, no text on the first and last lines, and all asterisks lined up. This style is suitable for long comments, or where attention is required.

Alternatively, the following style can be used:

/* This is another comment
   that also consists of several lines */

That is, lines are lined up vertically and the closing */ is on the last text line. This style is suitable for slightly shorter multi-line comments.

//-style comments may also be used, but try to avoid mixing the different comment styles too much. They should be written without leading/trailing commented lines:

// This is a comment
// that consists of multiple lines

Additionally, //-style comments can be appropriate for winged comments where horizontal space is scarce.

Do not use a comment style other than these mentioned other than in very special circumstances. In particular, do not use banners, boxes or horizontal/vertical lines of characters. These just take up space for no good reason, and grab attention that is better directed to code.

Consider comments to be statements for brace purposes. That is, the if-statement

if (drunk(user)) {
        /* sober up */
        drink(user, strong_coffee);
}

needs braces as if the comment had been a statement.

These rules are for visual consistency, to make it easier to locate, read and edit comments.

Do not use comments to disable (comment out) code; use #if 0 (or better, #if SOMESYMBOL). Exceptions are #defines which may be useful to turn on in special circumstances:

/* Turn on to get verbose printouts at each conditional branch */
/* #define DEBUG_COND_BRANCH */

Do not check in disabled code without a very good reason for doing so and a comment stating why it is there. Lacking this, disabled code is fair game for removal without prior notice.

4.2 Contents of comments

Comments should only contain information that cannot be easily inferred from the code. If the code is obvious enough, no comment is needed. If not, it is better to spend effort on making the code clearer than explaining it in a comment.

Example of a bad comment:

/* Flush page cache. */
flush_page_cache(cpu);

Explain why, not what. Reading the code gives you what, but not always why. Reasons for a particular design choice are much more useful to the reader. Do not sign comments with name or date.

Do not keep history in comments. They should describe the code as it is, not as it has been. Erase anything that is no longer valid.

Examples of bad comments:

/* moved here from processor.c */

double delta;   /* no longer an integer */

/* (mike) this is only safe if x != 0 */

/* 980325 rewritten to use new event code */

When editing existing code, you are just as responsible for editing the comments that refer to that code so that they are still valid. Incorrect comments should not be left in the code; it is better to remove them if they cannot be updated to reflect the state of the code.

Partly for this reason, it is desirable to keep comments as close as possible to the code they are commenting on. This makes them harder to miss when changing the code. (Do not overdo this and fragment the code with too many interspersed comments—try to strike a balance.)

TODO and FIXME comments should make it clear what needs to be done or fixed, and why; otherwise they contain no information.

Refer to Bugzilla bug numbers in comments if the issue is still open. When fixed, such references should be removed. Example:

/* FIXME: This is incorrect if p==0. (bug 4711) */

Prefer describing data to explaining code. This should be evident to experienced programmers: If the data structures are known, the code manipulating them should be natural and need little extra explanation.

4.3 API documentation

Exported functions and types should be documented in a way that the Simics documentation tool can parse:

/*:: add function to-section processor-api-functions
short: Run processor sideways

Instead of executing forwards or backwards, run sideways for `n` cycles. 
`direction` can be either `Left` or `Right`.

## Exceptions

**General** Thrown when given an invalid argument.

## Return Value
The number of cycles actually executed.

## See Also
[`SIM_continue`]
*/

cycles_t
SIM_run_sideways(cycles_t n, direction_t direction)
{
        ...
}

The Simics documentation markup should not be indented. Do not use the Simics documentation markup for comments that are not used to generate documentation, such as in file comments.

4.4 File comments

Comments at the beginning of source code may contain a brief description of the file if not evident. Ordinary comment rules apply. If copyright and license statements are required, they should also be added to the top comment section.

Other than this, keep file comments to an absolute minimum, in accordance with the general comment principles above.

5 Preprocessor usage

If an #else or #endif is separated from its corresponding #if or #else by more than a trivial amount of lines, add a comment stating the condition for inclusion of the code below (for #else) or for the code above (for #endif):

#ifdef GREAT_CODE
...
#else  /* not GREAT_CODE */
...
#endif /* not GREAT_CODE */

This avoids needless editor trips to the top #ifdef just to see under what circumstances some lines are compiled. For the #else, inverting the original condition makes sense verbally (read “else, if not COND”). For the #endif, the corresponding #else or #if may not be visible so the only comment that makes sense is the one that describes the code ended by the #endif. This agrees with other code standards such as GNU.

Use guards to prevent multiple inclusion of a header file:

#ifndef HEADER_FILE_H
#define HEADER_FILE_H
...
#endif

Include sufficient amounts of the file path in the name of the guard for it to work even when multiple headers have the same name. For example, the file src/weapons/nuclear/little-boy.h could have the header guard WEAPONS_NUCLEAR_LITTLE_BOY_H.

Use shallow (1-space) indentation to make preprocessor conditions more readable. Indent the whole directive, not just the word after the #:

#if defined HOPE && defined GLORY
 #include "honour.h"
 typedef longsword_t weapon_t;
 #if !defined SANITY
  #define BERSERK 1
 #else
  #define BERSERK 0
#else
 #include "defeat.h"
 typedef nuke_t weapon_t;
#endif

If used carefully, this makes the above-mentioned comments less frequently needed, unless the conditionals span great distances. Small declarations (like the typedef in the example) may be indented similarly, but keep larger declarations and definitions (such as function definitions) in column 0.

5.1 Macros

Macro names should be in upper case. Their formal arguments should be in lower case and parenthesised when used if they represent expressions.

If a macro contains multiple statements, surround them with do { ... } while (0). Macros intended to return a value should have parentheses around the expression if needed to allow them to be used in any expression context. Macros that expand to constants need no parentheses.

Always right-justify the backslashes in multi-line macros, to make them easier to read (C-c C-\ in Emacs).

Examples:

#define THE_ANSWER_TO_EVERYTHING 42

#define COMPOUND_SCORE(p) ((p)->score + (p)->bonus)

#define FROBBLE(n, type)                \
do {                                    \
        type _x;                        \
        gurgle_ ## type(&_x, (n) + 1);  \
        whistle(_x);                    \
} while (0)

Always prefer using inline functions rather than macros if possible. Be careful when declaring variables inside macros; give them names that are unlikely to be used by actual parameters, to avoid accidental capture.

6 Naming

In absence of other rules, identifiers are written in lower case letters, words separated by underscores.

6.1 Functions, macros and variables

Functions and macros that are executed primarily for their side-effect should be named after what they do. Functions and macros executed for their return value should be named after what they return. If the function or macro is a predicate (returning a boolean value), it should be named after the condition when it returns a true value.

Examples:

void show_death_animation(monster_t *m);
float magic_power(monster_t *m, int colour);
bool is_undead(monster_t *m);

Variables should be named after what they contain, not from the variable or its type. The more local a variable is, the shorter can be its name. Use long, descriptive names for global variables; use short names in local scopes. Names more frequently used can also be shorter.

Do not append a number as a general method to create new identifiers, other than in very special circumstances:

void draw_line(int x1, int y1, int x2, int y2); /* good */
int invalidate_object2(conf_object_t *obj);     /* BAD */

In particular, do not use “tmp” or “ptr” in identifiers; it is rare that it is needed to point out that a variable contains a temporary value or a pointer.

Do not prefix names with an article, such as an_object or the_score.

6.2 Types

Enum members are capitalised, each word separately. To avoid namespace clashes, consider using a common prefix:

enum monster_state { Sleeping, Awake, Angry, Fleeing };
enum shape { Sh_Rect, Sh_Rounded_Rect, Sh_Circle };

Typedef names should end in _t. Typedef structs, unions and enums unless only used locally. Do not define tags unless needed. If a struct/enum/union tag is defined, make it equal to the typedef but without the _t suffix.

Where possible, make struct definitions private to code if other parts of the source only need to handle pointers to the struct.

6.3 Files

In file names, words are separated by hyphens rather than underscores.

7 Code arrangement

The functions and variables exported from a .c file should be declared in the corresponding .h file. That header should be included first in the .c file.

This practice forces header files to be independent so that they do not require any other headers to be included first, which simplifies their use elsewhere. Making a unit include its own header will check that the definitions in both files agree.

Function prototypes in the header should not be declared extern; that keyword is superfluous there. The header should only contain the types actually needed for other units to interface with it. Where possible, opaque struct and class types should be used.

Any functions or variables that are not used outside the unit should be declared static.

Reorder functions to avoid the need of forward declarations where possible.

Forward declarations are just a pointless exercise required by the language, needing extra maintenance and taking up space. Ordering functions in the calling order also makes it easier to navigate in the code since it imposes a consistent direction to look for functions and their callers.

8 Various issues

Avoid assignments inside expressions, unless needed for flow control reasons:

if ((err = hurt_enemy(e)) < 0) ...           /* BAD */

err = hurt_enemy(e);
if (err < 0) ...                             /* GOOD */

while ((victim = next_target()) != NULL) ... /* GOOD */

This makes the expressions simpler to analyze and immediately understand; side-effects require some further thought. It also saves on parentheses and line length.

Use NULL instead of 0 as a null data pointer. Use (type *)0 as a null function pointer.

NULL is a pointer, 0 is an integer; the choice sends a strong message to the reader about the intention of the code. Unfortunately, the use of NULL as a function pointer cannot be used in portable C, hence the need to use 0, cast as appropriate. Using 0 instead of a pointer type as argument to a vararg function is undefined and can (and will) cause crashes.

Avoid casts where possible, since this can hide errors while suppressing warnings:

  • Do not cast pointers to/from void *
  • Use intermediate variables to convert a void * to a specific pointer.
  • Take the address of substructures instead of casting struct pointers.

Examples:

void *p = ...
int strength = ((troll_t *)p)->strength;   /* BAD */

troll_t *t = p;
int strength = t->strength;                /* GOOD */

save_object((conf_object_t *)cpu);         /* BAD */
save_object(&cpu->obj);                    /* GOOD */

When comparing an expression against a constant, put the constant last:

if (2 == x) ...              /* BAD */
if (x == 2) ...              /* GOOD */

This is more intuitive and scans better, since it corresponds more closely to how you would pronounce it in natural language (“if x is equal to two”, never “if two is equal to x”, since “two” is not likely to change.)

8.1 Switch statements

Always indicate a switch case fall-through with a comment.

switch (monster->state) {
case Sleeping:
        wake_up(monster);
        /* FALLTHROUGH */
case Awake:
        attack(monster, player);
        break;
case Dead:
        rattle_bones(monster->corpse);
        break;
}

All other cases should have a break statement, even the last case in the switch, unless they use a return/continue/goto to transfer control elsewhere.

Blocks inside switch clauses, when needed for local variables, do not introduce a new indentation level:

switch (cmd.type) {
case Sail: {
        double distance = hypot(cmd.x, cmd.y);
        double direction = atan2(cmd.y, cmd.x);
        go(direction, distance);
        break;
}
case Anchor:
        drop_anchor(current_position);
        break;
}

8.2 Boolean expressions

You may use implicit comparison against 0 in conditions for boolean values only. This includes pointers and other values where 0 can be interpreted as falsehood:

typedef enum { Red, Blue } colour_t;
colour_t halo_team(player_t *p);
...
if (halo_team(p)) ...          /* BAD - not a boolean */

monster_t *m = make_gelatinous_cube();
if (m) ...                     /* Good - NULL is false */

For example, a function returning zero on failure and a positive result otherwise could be used in boolean context.

Expressions where 0 is not intuitively understood as false must always use explicit comparisons. In particular, the strcmp function does not return a boolean value:

if (!strcmp(login, "root")) ...      /* BAD */
if (strcmp(login, "root") == 0) ...  /* GOOD */

This is also true for calls that return -1 on failure and 0 on success:

if (rmdir(game_dir)) ...                 /* BAD */
if (rmdir(game_dir) == -1) ...           /* GOOD */
if (rmdir(game_dir) < 0) ...             /* GOOD */

The following will help following these rules when using Emacs. Place in your .emacs file:

(setq load-path (cons "/home/packages/vt-elisp" load-path))
(load "vt-elisp-start")

This does not absolve you from doing the right thing where Emacs is wrong (which, unlikely as it sounds, may happen occasionally).
